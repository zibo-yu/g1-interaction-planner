# ELF3 URDF geometry proxy for the Stage-1 planner

This extension calibrates the **task-space planner's geometric proxy** using the two supplied ELF3 URDF files. This is **not** a SOMA adapter, IK, or proof of reachability.

## Windows usage

From PowerShell in the repo root, after installing the Version-1 requirements:

```powershell
.\.venv\Scripts\python.exe tools\elf3_proxy_calibration.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_elf3_proxy.py" -v
.\.venv\Scripts\python.exe -m handshake_mpc.demo --scenario near --config configs\elf3_proxy.json --output outputs\elf3_near
```

The last command reuses the **original** demo scenario's human hand targets, which were designed for the default humanlike geometry; they are *not* geometrically calibrated to ELF3. For a meaningful ELF3 demo, derive contact target positions using the new negative-X robot-right convention and the calibrated wrist/torso offsets. Original demo assertions may therefore fail with the proxy config without indicating a code defect.

## Inputs and outputs

- `models/elf3.urdf`: original upload, wrist visual meshes `*_wrist_z_link.STL`.
- `models/elf3_hand_mesh.urdf`: second upload, wrist visual meshes `l_hand.STL` and `r_hand.STL`.
- `tools/elf3_proxy_calibration.py`: stdlib XML + NumPy FK and profile generator.
- `configs/elf3_proxy.json`: MPC configuration containing derived approximate geometry.
- `calibration/elf3_geometry_report.json`: all derived quantities, joint limits, assumptions, and exclusions.
- `tests/test_elf3_proxy.py`: unit checks against both models and exact URDF link transforms.

## Anatomical definitions

ELF3 uses **+Z upward and +X forward**, with +Y toward the robot's left. Our MPC is **+Y upward and +Z forward**, with +X toward the robot's left. The proper rotation mapping one basis to the other is

```
[x_planner, y_planner, z_planner] = [y_elf3, z_elf3, x_elf3]
R_planner = M @ R_elf3 @ M.T
```

`pelvis` is a **virtual frame** at the midpoint between hip joint origins (`l_hip_y_link`, `r_hip_y_link`) in the zero-joint configuration, not `torso_link`. At zero joints, pelvis is 0.3825 m below `torso_link`; robot-right shoulder is `[-0.178, 0.4695, 0.0]` m relative to the pelvis in planner coordinates.

## What URDF determines versus what it cannot

Derived from URDF:
- relative shoulder, torso, hip and wrist link origins in zero-joint configuration;
- shoulder-elbow and elbow-wrist nominal segment lengths, 0.256 m each;
- revolute joint axes and limits;
- a verified sample reaching FK posture `r_shoulder_y_joint=-0.55`, `r_wrist_y_joint=+0.55` rad, with zero global wrist rotation.

**Not determined by supplied files:**
- physical hand-tip position or collision/contact geometry: the files refer to mesh files but the meshes were not supplied, and there is no fixed `right_hand_tip` link;
- true neutral standing joint configuration or foot-sole contact height: the `.64 m` pelvis height assumes zero-joint ankle origins on the ground and is only a proxy;
- comfortable workspace and hand-tip offset: the comfort box half-widths and `0.12 m` tip offset are still heuristics;
- achievable pelvis walking speed or wrist acceleration: revolute velocity/effort limits do not imply these task-space bounds;
- actual reachability under orientation, joint, self-collision, and balance constraints;
- SOMA skeleton dimensions or valid KiMoDo `constraints.json`.

`max_pelvis_wrist_distance_m=0.8` is intentionally retained as a conservative **radial cap**, not a reachability certificate. The triangle-inequality upper bound for nominal upright torso shoulder-to-wrist geometry plus pelvis-to-shoulder offset is approximately 1.014 m, but many points *inside* a sphere remain unreachable.

## Next integration step

Use this profile to exercise task-space planning with approximate ELF3 geometry. For native KiMoDo input, keep `handshake_task_space/v1` as the neutral interop boundary, then obtain a **SOMA** reference skeleton/pose and run a SOMA FK/IK round-trip to form `root2d` and `right-hand` constraints. **Do not** plug the ELF3 URDF joint rotations directly into SOMA constraint JSON.

## ELF3-consistent mock reach test

The original demos use humanlike targets on positive X. The added ELF3-specific example derives a **robot-right** (negative-X) wrist target from the FK seed reach pose and adds the provisional tip offset:

```powershell
.\.venv\Scripts\python.exe examples\elf3_proxy_demo.py
```

It writes `outputs/elf3_proxy_reach/executed_states.csv` and `last_predicted_horizon.json`. These are generated by the synthetic feedback loop and remain **task-space references**, not native KiMoDo constraints. This example is included for Windows testing and was not executed in the current Linux environment, which lacks the original CVXPY dependencies; the eight ELF3 geometry tests were executed successfully.
